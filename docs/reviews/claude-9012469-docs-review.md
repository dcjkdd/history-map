## 2. 核心诊断：工程开发与内容审核之间缺少安全的连接方式

### 2.1 现象

`信息项`

ADR-0001 收敛了 Go、PostGIS、RAG、3D 等工程范围，但内容侧的流程复杂度在反向增长：

- [anshi-mvp-content-review.md](anshi-mvp-content-review.md) 的审核表有 11 个核对列。
- [anshi-mvp-source-notes.md](../../data/curated/anshi-mvp-source-notes.md) 要求逐条 `claimId` 绑定 `citationId`，空间数据要核对许可证链接、署名文字、原始坐标系、裁剪/简化/重投影过程。
- [mvp-acceptance.md](../plans/mvp-acceptance.md) 第 9 节要求产品负责人、内容负责人、开发负责人三方签字，而这三个角色是同一个人。
- 当前结果：`当前批准记录数：0`，四个 Source 全部为"待填写"，`MVP-03` 状态为 `BLOCKED_BY_CONTENT`。

### 2.2 问题的准确表述（初版表述已修正）

`信息项`

初版把问题表述为"内容状态是二元的，只有空数据集和全部 `APPROVED` 两档"。**该表述不准确**：内容流程中存在 `PENDING_REVIEW`，且 [mvp-tasks.md](../plans/mvp-tasks.md) 第 3 节明确允许 `MVP-05` 使用"正式或**审核中**数据"。中间档在流程上是存在的。

更准确的表述是：

> 中间档只存在于**内容流程**中，不存在于**运行时数据**中。[mvp-acceptance.md](../plans/mvp-acceptance.md) 第 2.2 节第 5 条明确规定"发布 JSON 本身不需要携带审核状态"。这是有意设计，但它导致运行时无法区分"审核中数据"与"发布数据"，因此工程开发与内容审核之间缺少一条安全的连接方式。

后果是实际存在的：`MVP-05`（图层）、`MVP-06`（时间轴）、`MVP-07`（路线逐段显隐）、`MVP-08`（详情与引用）、`MVP-09`（整合布局）目前只能面对 0 个 feature 的 FeatureCollection 开发，而路线显隐、图层可辨识度、侧栏信息密度、布局压力都无法在空数据集上验证。

### 2.3 建议：开发数据集（方案已按复核意见修正）

`部分采纳（方案已修正）`

概念成立，但**初版给出的实现位置是错误的**。

初版建议放在 `frontend/public/data/anshi/mvp-dev.json`，并称"通过环境变量切换，生产构建默认不包含"。该说法在本工程中不成立：Vite 的 `public/` 目录内容会被原样复制到 `dist/`，环境变量无法排除。已实测验证：

```text

628ba71579bb94dc97579b2aebdcdb94da1f2c826e5e7f535c9da92de4d3357d  frontend/dist/data/anshi/mvp-v1.json
```

修正后的方案约束（供用户决策，未采纳前不实施）：

1. **开发数据集必须位于生产静态目录之外**，不得放入 `frontend/public/`。
2. **必须有自动测试证明生产构建产物不包含该数据集**，而不是依赖约定或环境变量。这是本条的硬性前提，缺少该测试则不应采纳。
3. **地名一律使用无历史指向的假名**（如"示例关隘 A""示例都城 B""示例河流甲"），不得使用潼关、长安、洛阳、陕州、灵宝等真实地名。即使文件被误发布，也不会产生任何伪造的历史结论。
4. 坐标使用明显规则化或明显非叙事区域的坐标，进一步杜绝误用。
5. 数据量按 [mvp-acceptance.md](../plans/mvp-acceptance.md) D-001 的真实目标构造（约 15 地点 / 12 事件 / 4 路线 / 20 分段 / 6 地理要素），目的是让布局与性能问题在真实规模下暴露。
6. 该数据集必须通过 `npm run validate:data` 同一套校验，不得为它放宽任何规则。

**时点**：不在当前采纳。`MVP-04` 使用现有技术空数据集即可完成地图容器与降级底图，不被内容阻塞。进入 `MVP-05` 前，若正式或审核中内容仍未就绪，再单独设计并决策本方案。

## 3. 史料与空间数据的定位方式

`已处理`

[anshi-mvp-source-notes.md](../../data/curated/anshi-mvp-source-notes.md) 与 [anshi-mvp-content-review.md](anshi-mvp-content-review.md) 都写了"页码**或**稳定定位"，方向正确，但登记表列名与多处措辞向"页码"倾斜，容易让人误以为必须先取得纸质版并核对页码。

建议在 [03-史料引用与数据可信度.md](../data/03-史料引用与数据可信度.md) 中把优先级明确写死：

1. **正史与编年史优先使用「书名·卷次·纪传/年条」作为稳定定位，而非页码。** 卷次在不同版本间稳定，页码随版式变动；配合公开可访问的稳定 URL 后，任何人可独立复核，可复核性严格优于页码。
2. 现代研究著作因无稳定内部编号，仍以"版本 + 章节 + 页码"为准。
3. 摘录边界不变：仍受 [mvp-acceptance.md](../plans/mvp-acceptance.md) D-008 约束，以项目归纳为主，原文摘录短小必要。

本条**不需要修改数据契约**，只是录入优先级的文档澄清；现已写入 [03-史料引用与数据可信度.md](../data/03-史料引用与数据可信度.md)。

补充说明（`信息项`）：古籍原文属于公有领域，但现代点校本的标点、分段、校勘记与版式属于整理成果，受保护。以卷次定位加项目归纳为主的策略，成本更低，法律边界也比大量摘录点校本更清晰。

关于空间数据（`信息项`）：`SRC-SPATIAL-01` 现有的核对要求（原始坐标系、覆盖范围、访问日期、裁剪/简化/重投影过程、许可证链接、署名文字）合理，建议保持。选用公有领域数据集可降低署名与许可负担，但具体数据集的版本、许可证与署名要求**必须由用户实际核对后登记**，Codex 不得代为断言任何数据集的许可证状态。

### 4.1 城池控制权随事件变化

2. 数据集带 `schemaVersion`，新增一个顶层数组是向后兼容变更（1.0 → 1.1），**延后实施几乎不增加成本**。因此现在不做是净收益。

留档备查的最小形态（不实施）：

```text

  { placeId, fromEventId, controlledBy: side, certainty, citationIds }

```

渲染规则与 `appearAtEventId` 同构（取 `sequence` 小于等于当前事件的最后一条），是既有机制的复用而非新机制。若将来采纳，需同步增加悬空引用校验，并为每条 `placeState` 追加审核行。

### 4.2 路线段的结束条件

`延期`

`appearAtEventId` 是单向的，路线段一经出现即永久可见。本期叙事切片包含往返结构，存在方向叠加导致视觉混淆的可能。

**本版结论为延期。** [mvp-acceptance.md](../plans/mvp-acceptance.md) A-012 明确要求路线段自 `appearAtEventId` 起持续存在，且"是否真的视觉混乱"属于需要真实页面验证的问题，不应凭推演修改验收标准。建议在 `MVP-07` 完成后以真实数据观察，确有问题再决定。

留档备查的最小形态（不实施）：可选字段 `activeUntilEventId`，语义为超过该事件后降为弱样式**而非消失**，以保持"已发生的历史不会被撤销"的心智。同样属于向后兼容变更。

### 4.3 `certainty` 语义

`已处理`

初版称 `certainty` 的所指"不明确"，**该判断说重了**。[mvp-tasks.md](../plans/mvp-tasks.md) 第 2.4 节实际已逐个定义：Place 为"坐标或对应关系可信度"、Geography 为"重建可信度"、RouteSegment 为"路线重建可信度"、Event 为"时间或事件细节可信度"。

修正后仅保留一处具体意见：**Event 的 `certainty` 定义为"时间**或**事件细节可信度"，是用一个值覆盖两类不同对象**。当史料对时间明确但对过程有分歧（或相反）时，该字段无法表达。

处理方式是一句话级的澄清，不改模型：Event 级 `certainty` 表示事件存在性与时间定位，过程、因果和叙事解释的可信度归各自 `SourcedClaim`。该语义已写入 [mvp-tasks.md](../plans/mvp-tasks.md)。

另一条独立建议也已处理：`side` 枚举中，`TANG` 表示前线唐军等军事行动主体，`COURT` 表示朝廷政治决策或转移主体。本期叙事切片包含朝廷决策与前线判断的分歧，两者若在录入时混用，该分歧将无法呈现。本条同样是文档澄清，不改契约。

## 5. 验收标准相关

### 5.1 引用粒度与数量目标的换算关系

`已处理`

[mvp-acceptance.md](../plans/mvp-acceptance.md) D-005 要求"每条对外展示结论至少关联一个 Citation"。按 D-001 的数据量目标估算：

- 10—15 个 Event × (`summary` + `whyItMatters`) ≈ 20—30 条 Claim
- 12—20 个 Place × (`summary` + `strategicRole`) ≈ 24—40 条 Claim
- 10—25 个 RouteSegment + 4—8 个 Geography 的解释性文本 ≈ 15—35 条 Claim

合计约 **60—100 条 Claim**，而 Citation 数量下限仅为 15 条，即平均每条 Citation 需支撑 4—6 条 Claim。

这在史料实践中是正常的（编年史的一段记载确实可支撑多个判断），但当前文档未点明该换算关系，录入阶段容易被误解为"每条 Claim 必须使用独立 Citation"，从而产生要求自相矛盾的错觉。

现已在 D-005 明确写出：**一条 Citation 支撑多条不同 Claim 是预期形态，不构成引用粒度不足。** 每条 Claim 仍须显式绑定实际支持它的 Citation。本条为文档澄清，不改数量门槛。

是否同时把 Citation 下限提高到 25—30，由用户决定；本版不作为建议提出。

### 5.2 1024×768 下限

`延期`

初版建议将最低分辨率目标从 1024×768 提高到 1280×800。**本版改为延期。**

理由：初版依据是估算（该分辨率下地图可用区约剩 600×450），而 [mvp-acceptance.md](../plans/mvp-acceptance.md) A-019 的实际要求只是"核心功能可操作"，并未要求三块区域始终完整展开。应在 `MVP-09` 实测真实布局后再决定，不应凭估算修改验收标准。

独立于分辨率结论的一条建议保留：**侧栏可折叠对所有分辨率都有收益**，可在 `MVP-09` 一并考虑。

### 5.3 外部 AI 交叉审查的频率

`部分处理`

[reviews/](.) 下已有的外部审查产出为：MVP-01 阶段 3 个 P3，MVP-02 阶段 1 个 P2，均无 P0/P1。而每轮成本包含打包、计算 SHA-256、上传、限时审查、逐条裁决、撰写审查记录。

因此本条不是新增功能，而是**在已排期的地理要素预算内，决定该 `CORRIDOR` 要素录成什么几何形态**：一条示意线，还是一个能表达可通行范围宽度的面。两者的数据契约、图层数量、构建依赖完全相同，差异只在几何本身与录入成本。

建议倾向后者，理由是项目差异化命题为"用地形解释战争"，而宽度带能让用户不依赖文字即理解空间约束，也是 [mvp-acceptance.md](../plans/mvp-acceptance.md) D-007 第 1、2 问最直接的回答方式。它不需要 DEM、3D 或坡度分析，完全落在当前二维静态边界内。

**决策时点是 `MVP-03` 录入几何时，而非"以后"**：几何一旦按示意线录入并完成签字，改为宽度带需重走一次几何审核。选择规则和审核约束现已写入 `mvp-tasks.md`、资料笔记与内容审核表，但具体几何形态仍须在 `MVP-03` 依据资料决定。

约束不变：该几何属解释性重建，必须标 `INFERENCE`、可信度不高于 MEDIUM、附几何来源与处理过程说明，**不得凭视觉印象手绘**。
