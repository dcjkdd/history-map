## 1. 结论

现有文档中的长期产品方向和目标技术栈总体合理，真正的问题不是“技术选错了”，而是：

> **长期目标架构、专题完整形态和第一期 MVP 被放在了同一个实施层级。**

如果第一期同时建设 Go API、PostgreSQL/PostGIS、sqlc、goose、完整领域模型、数据后台、人物/战役详情页、自动时间轴、RAG 和三维地形，会在产品价值尚未验证前投入大量基础设施工作。

第一期建议改为一个可独立发布的、只读的前端垂直切片：

```text
浏览器
└── Vue 3 + TypeScript + Vite + MapLibre GL JS
    ├── 二维地图
    ├── 地点、地理要素和路线图层
    ├── 离散事件时间轴
    ├── 事件 / 地点详情
    └── 史料引用与可信度
             │
             ▼
    静态版本化数据集 mvp-v1.json
```

本期暂不建设后端和数据库，但数据结构应按未来 API 响应设计，并通过单独的数据访问层加载。以后切换为 Go API 时，地图组件和业务组件不需要重写。

## 2. MVP 要验证的产品假设

第一期不是验证“能否做一个中国历史 GIS 平台”，而是验证三个更具体的问题：

1. 用户能否通过地图和事件顺序理解潼关在长安东部防线中的空间作用。
2. 路线随事件逐段出现，是否比静态战争路线图更容易理解战争进程。
3. 地点、事件和战略解释附带来源与可信度，是否能形成区别于普通历史地图的信任感。

### 2.1 一条完整用户路径

用户进入页面后，应能在不阅读使用说明的情况下完成：

1. 看到长安、洛阳、陕州、灵宝、潼关及黄河、渭河、秦岭等关键空间关系。
2. 从第一个事件开始，使用“上一事件 / 下一事件”浏览关键节点。
3. 看到叛军推进、唐军防守或出战路线随事件逐段出现。
4. 点击潼关、灵宝、长安等地点查看战略作用。
5. 查看事件或地点对应的资料、章节或页码，以及可信度说明。
6. 在 5—10 次交互内讲清“为什么潼关关键、出关后为什么局势迅速恶化”。

## 3. 现有设计的过度设计检查

| 现有设计 | 判断 | 第一期处理 | 原因 |
|---|---|---|---|
| Vue 3 + TypeScript + Vite | 保留 | 必须实现 | 足够轻量，适合交互地图 |
| MapLibre GL JS | 保留 | 必须实现 | 二维 GeoJSON 图层和后续地形演进都适合 |
| Pinia | 缩减后保留 | 仅一个 MVP 状态仓库 | 时间轴、选中对象、图层状态需要共享，但不建立复杂 store 体系 |
| Vue Router 与多详情页 | 暂缓 | 仅单页地图，不建 `/place`、`/battle`、`/person` 页面 | MVP 详情用侧栏即可，路由和深链接不是核心验证点 |
| ECharts | 暂缓 | 时间轴使用 Vue 组件和普通 DOM/CSS | 当前没有复杂统计图，ECharts 只会增加依赖和交互耦合 |
| Element Plus / Naive UI | 暂缓 | 使用少量自建基础样式 | 第一版组件很少，不值得引入完整 UI 框架 |
| Go + Gin API | 暂缓 | 不建设运行时后端 | 本期数据只读且规模很小，HTTP 业务层不能增加产品验证价值 |
| PostgreSQL + PostGIS | 暂缓 | 不启动数据库 | 本期不需要范围查询、空间相交、后台编辑或多专题查询 |
| pgx + sqlc + goose | 暂缓 | 不引入 | 这些依赖于数据库，当前会形成迁移、生成代码和部署负担 |
| Martin / MVT / PMTiles | 暂缓 | GeoJSON 直接加载 | MVP 数据规模远未达到瓦片化需求 |
| 完整 Topic / Period / Person / Battle / PlaceName 领域模型 | 缩减 | 固定一个专题；Battle 合并为 Event 类型；人物先作为事件参与者文本 | 先验证叙事，不先建设通用历史平台模型 |
| Route + RouteNode 概念 | 保留思想、简化实现 | 使用带事件显隐条件的 RouteSegment GeoJSON | 必须支持逐段出现，但无需数据库节点表 |
| Source + Citation | 保留 | 必须实现 | 这是产品差异化，不属于过度设计 |
| 可信度和观点类型 | 保留 | 必须实现最小集合 | 历史坐标、时间和结论存在不确定性，不能全部展示为确定事实 |
| 简单数据维护后台 | 暂缓 | 直接维护版本化 JSON | 后台会带来表单、权限、校验和发布流程，MVP 阶段投入过大 |
| QGIS / GDAL | 作为离线工具按需使用 | 不进入运行时架构 | 少量点线可人工整理；需要校正几何时再使用 QGIS |
| RAG、pgvector、Python Worker | 暂缓 | 不实现 | 没有经过验证的引用展示前，不应先做自动问答 |
| 3D Terrain、DEM、hillshade、deck.gl | 暂缓 | 只做二维 | 第一阶段先验证信息组织和叙事；三维属于后续增强 |
| 自动播放、移动军队图标、粒子动画 | 暂缓 | 使用离散事件切换 | 连续动画开发和调参成本高，也容易制造错误时间精度 |
| 数据校验和基础测试 | 保留 | 必须实现 | 历史数据引用关系复杂，校验不是“工程洁癖”，而是内容可信度底线 |

## 4. 第一期推荐架构

### 4.1 运行时架构

```text
Vue 单页应用
├── AppShell
├── HistoryMap
│   ├── GeographyLayer
│   ├── PlaceLayer
│   ├── RouteLayer
│   ├── LayerControl
│   └── MapLegend
├── EventTimeline
├── DetailPanel
│   ├── EventDetail
│   ├── PlaceDetail
│   └── CitationList
└── MVP Store
        │
        ▼
MvpRepository
        │
        ▼
/public/data/anshi/mvp-v1.json
```

### 4.2 数据迁移边界

为避免静态版成为一次性代码，必须保持以下边界：

1. UI 组件不得直接 `fetch` 数据文件，只能通过 `MvpRepository`。
2. 数据集必须带 `schemaVersion`。
3. 地点、地理要素和路线使用 GeoJSON 几何，坐标统一为 WGS84（EPSG:4326）。
4. 所有实体使用稳定字符串 ID，不使用数组下标作为引用。
5. 将来 Go API 可直接返回同形状数据：`GET /api/v1/topics/anshi/mvp`。
6. 将来切换到 PostGIS 时，仅替换数据来源和查询实现，不改变地图组件输入结构。

## 5. 第一期必须实现的功能

### 5.1 P0 功能

| 功能 | 最小实现 |
|---|---|
| 二维地图 | MapLibre 地图可缩放、拖动；无外部底图配置时仍有可用的空白底图降级方案 |
| 基础地理信息 | 展示与核心叙事直接相关的河流、山脉或通道示意，不建设全国地理数据集 |
| 历史地点 | 展示城池、关隘和关键节点；不同类型有可区分样式 |
| 路线 | 展示 3—5 条核心行动路线，路线按事件拆为可逐段显隐的线段 |
| 图层控制 | 至少可独立开关地理要素、地点、路线 |
| 离散事件时间轴 | 支持选择事件、上一事件、下一事件；不做连续日期拖动和自动播放 |
| 地图与时间轴同步 | 选择事件后，高亮相关地点和本事件已发生的路线段；未来路线不得提前显示 |
| 地点详情 | 名称、现代位置说明、类型、战略作用、坐标可信度、相关引用 |
| 事件详情 | 时间文本、事件摘要、为什么重要、相关地点、相关路线、引用和可信度 |
| 史料引用 | 显示资料、作者/版本、章节或页码、观点类型；原文摘录可选且应短小 |
| 可信度展示 | 至少支持 HIGH / MEDIUM / LOW / DISPUTED / UNKNOWN，并显示文字说明 |
| 图例与状态提示 | 用户能理解地点类型、路线阵营、可信度和当前时间节点 |
| 数据校验 | 构建前检查 ID、引用、时间顺序、坐标、路线段和引用完整性 |
| 异常状态 | 数据加载失败、底图不可用时有明确提示，页面不能白屏 |

### 5.2 MVP 内容量目标

第一期内容应集中在“潼关防线—灵宝出战—长安失守”这一条叙事链，不追求覆盖 755—763 年全部战线。

2026-07-30 经用户确认，MVP-03 采用缩小版内容规模。该决策以验证叙事地图的最小产品价值为目标，替代此前较大的数量目标；后续扩充不再作为第一版验收前置。

| 内容 | MVP 目标 |
|---|---:|
| 专题 | 1 个 |
| 关键地点 | 5 个 |
| 离散事件 | 6 个 |
| 示意行动方向/逻辑路线 | 2 条 |
| 路线分段 | 2—4 段 |
| 现代地理背景要素 | 3 个 |
| 核心资料 | 2—3 种 |
| 引用记录 | 不少于 15 条 |

地点固定覆盖长安、洛阳、陕州、灵宝、潼关；现代地理背景固定覆盖黄河、渭河、秦岭。两条行动方向只表达有资料依据的宏观节点关系，必须明确标为解释性示意，不沿现代公路自动生成，也不主张精确复原历史路线。

东入关中通道仍可在正文中作为受黄河和山地约束的空间关系解释，但缩小版不要求将其制作成独立 `Geography` 几何。唐代河道复原、精确战场边界和额外地点均推迟到 MVP 验证之后。

## 6. 第一期明确暂缓的功能

| 暂缓项 | 暂缓原因 | 重新引入条件 |
|---|---|---|
| Go 后端与 REST API | 只读单专题无法体现后端价值 | 需要在线编辑、多个专题、用户数据或对外 API |
| PostgreSQL / PostGIS | 没有空间查询和并发写入需求 | 需要视野范围查询、空间关系计算、后台维护或数据量明显增长 |
| 数据维护后台 | 表单、权限、审核、发布链路会扩大范围 | 静态 JSON 维护已成为明显瓶颈，且数据模型已稳定 |
| 完整 755—763 年事件覆盖 | 会把内容研究变成第一期主要风险 | 潼关叙事切片通过产品验收后分批扩展 |
| 人物详情页、战役详情页 | 不影响核心地图叙事验证 | 用户对相关信息有明确需求，且数据量足够支撑独立页面 |
| 古今地名搜索 | 单专题地点少，列表和地图可直接浏览 | 地点超过人工浏览范围或开始支持多专题 |
| 时间轴自动播放 | 容易掩盖史料时间精度并增加状态复杂度 | 离散时间轴稳定，且有明确展示场景 |
| 连续行军动画、军队图标 | 动画调度和路径插值成本高 | 路线分段叙事价值已被验证 |
| 3D 地形、DEM、坡度分析 | 数据加工和地图服务复杂 | 二维版证明“地形解释战争”有用户价值 |
| Martin、MVT、PMTiles | 当前 GeoJSON 很小 | 数据量或首屏性能出现实测瓶颈 |
| RAG、AI 问答、自动文档导入 | 先要验证引用数据结构和内容质量 | 人工知识库积累到足够规模，且引用展示稳定 |
| 登录、笔记、协作修订 | 不属于核心浏览体验 | 产品公开运行且出现真实协作需求 |
| SEO、公开索引策略 | MVP 先验证产品，不做流量工程 | 准备公开发布并有稳定内容更新机制 |
| 完整移动端适配 | 地图和侧栏的移动布局会显著增加设计成本 | 桌面版验收通过后单独规划 |

## 7. MVP 最小数据结构

数据集顶层只保留当前页面真正需要的对象：

| 对象 | 用途 |
|---|---|
| `schemaVersion` | 数据格式版本，例如 `1.0` |
| `topic` | 专题名称、说明、初始地图视野、默认事件 |
| `places` | GeoJSON Point 集合，保存城池、关隘等地点 |
| `geography` | GeoJSON LineString / Polygon 集合，保存河流、山脉和通道示意 |
| `routeSegments` | GeoJSON LineString 集合，保存可按事件显隐的路线段 |
| `events` | 按 `sequence` 排序的离散事件 |
| `sources` | 书籍或资料的基础书目信息 |
| `citations` | 章节、页码、摘要、观点类型和可信度 |

### 7.1 建模原则

1. 时间轴以明确的 `sequence` 排序，不用虚构的精确日期强行排序。
2. 每个事件同时保存展示用 `dateLabel`；能确认时再保存标准化日期和精度。
3. 路线段通过 `appearAtEventId` 控制首次出现，不能根据前端动画猜测时间。
4. 战役先作为 `eventType=BATTLE` 的事件，不单建 Battle 实体。
5. 人物先保存为事件参与者名称和角色，不建设人物关系图。
6. 每条对外展示的事实、战略判断和项目推断都必须有稳定结论 ID，并逐条关联至少一个 Citation；不能只在实体级笼统挂一组来源。没有来源的内容标为待审核，不进入发布数据。
7. 低可信度坐标必须保存 `coordinateNote`，前端显示其不确定性。

## 8. 非功能边界

- 只读应用，不允许在线编辑。
- 以桌面浏览器为主要目标，最低保证 1024×768 下核心功能可操作。
- 数据集原始体积目标不超过 2 MB；不包含地图瓦片。
- 时间轴切换、图层开关和详情切换不应出现肉眼可见的长时间卡顿。
- 外部底图失败时，核心历史图层、时间轴和详情仍可使用。
- 控制台不得出现未处理异常。
- 所有构建均先执行数据校验；校验失败不得生成可发布版本。
- 不因为“视觉上更好看”而把不确定路线或坐标表现成精确事实。

## 9. 关键依赖和风险

### 9.1 内容输入是正式前置条件

当前项目文档给出了地点、路线和产品方向，但没有提供足够的页码级史料摘录。Codex 可以实现数据结构、地图和校验，**不能替代史料核对，也不能编造页码、坐标或争议结论**。

在填充正式 MVP 数据前，应准备一份人工确认的资料笔记，至少包含：

- 事件顺序和时间文本
- 地点对应关系及坐标依据
- 路线节点或大致走向
- 战略解释
- 资料名称、版本、章节、页码或稳定定位
- 逐条结论 ID、引用 ID 及其绑定关系
- 空间数据版本、许可证、许可证链接、署名要求和处理过程
- 不确定和争议说明

缺少上述输入时，可以完成技术骨架和示例数据模板，但不能宣布内容验收通过。

### 9.2 外部底图风险

MVP 不建设自己的瓦片服务。地图样式 URL 通过环境变量配置，并提供本地空白样式作为降级。公开部署前再单独确认底图服务的许可、配额和稳定性。

### 9.3 历史地图的“看起来精确”风险

路线是基于史料和现代地理的解释性重建，不应自动吸附现代道路。低可信度路线应使用较弱样式并显示说明。

## 10. MVP 完成定义

同时满足以下条件才算第一期完成：

1. 用户能通过时间轴完整理解一个“潼关防线—出战—失守”的核心故事。
2. 地点、地理要素和路线能在同一地图中清楚辨识。
3. 路线随事件逐段出现，未来信息不提前泄露。
4. 关键地点和事件都能查看资料出处与可信度。
5. 数据引用、ID、时间顺序和坐标通过自动校验。
6. 应用在无 Go 服务、无数据库的情况下可本地运行和静态构建。
7. 暂缓项没有以“顺便实现”的方式进入代码。
8. 内容负责人完成史料、坐标和叙事人工审核。
