# 后端技术栈（Go）

## 1. 推荐组合

| 能力 | 技术 |
|---|---|
| 语言 | Go |
| Web 框架 | Gin |
| PostgreSQL 驱动 | pgx |
| SQL 代码生成 | sqlc |
| 数据库迁移 | goose |
| 参数校验 | go-playground/validator |
| 配置 | cleanenv 或 Viper |
| 日志 | slog 或 zap |
| API 文档 | swaggo / OpenAPI |
| 数据库 | PostgreSQL + PostGIS |
| 向量检索 | pgvector（后期） |
| 矢量瓦片 | Martin（后期） |
| 文件存储 | MinIO（后期） |

## 2. 为什么采用 Go

- 业务以地图查询和 JSON/GeoJSON 输出为主
- 启动快、内存占用低
- 单二进制部署简单
- 适合频繁地图查询
- 项目早期不需要大型企业框架

## 3. 为什么推荐 pgx + sqlc

空间查询会大量使用 PostGIS SQL，例如：

```sql
ST_DWithin
ST_Intersects
ST_Contains
ST_Length
ST_Distance
ST_AsGeoJSON
ST_MakeEnvelope
```

手写 SQL 更直观，sqlc 可以生成类型安全的 Go 调用代码，避免重 ORM 对空间 SQL 的限制。

## 5. 地图接口演进

第一阶段：

```text
PostGIS → Go API → GeoJSON → MapLibre
```

数据增加后：

```text
PostGIS → Martin → MVT → MapLibre
```

Go 继续负责业务接口，Martin 只负责瓦片。

## 6. RAG 与 Go

Go 负责：

- 文件上传
- 任务管理
- 知识库查询
- 模型接口编排
- 引用返回

复杂文档解析和 OCR 后期交给 Python Worker。第一期不拆分。
