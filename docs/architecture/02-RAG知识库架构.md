# RAG 知识库架构

## 1. 建设原则

知识库不是让模型“背下整本书”，而是让系统在回答问题时检索相关段落，并返回明确出处。

目标回答结构：

1. 可确认的事实
2. 正史记载
3. 现代学者观点
4. 存在争议的部分
5. 资料名称、章节、页码和必要摘录

## 2. 推荐流程

```text
上传 PDF / EPUB / Markdown / 读书笔记
               ↓
文档解析
               ↓
章节识别和段落切片
               ↓
地点、人物、事件、年份实体提取
               ↓
人工确认关键实体与坐标关联
               ↓
Embedding
               ↓
PostgreSQL + pgvector
               ↓
地图点击 / 用户提问
               ↓
按专题、地点、人物、时间过滤检索
               ↓
重排、生成回答、附带引用
```

## 3. 分阶段实现

### 第一阶段：人工知识库

不做自动 RAG，先录入：

- 资料名称
- 作者、版本、出版信息
- 章节和页码
- 原文摘录
- 自己的归纳
- 关联地点、人物、事件、战役
- 观点类型和可信度

优点是数据可靠，能先验证产品结构。

### 第二阶段：半自动导入

- 自动解析 PDF、EPUB、Markdown
- 自动切片
- 自动提取人名、地名、年份
- 人工确认后入库

### 第三阶段：带引用问答

- pgvector 检索
- 专题和时间过滤
- 多资料对照
- 回答附带引用
- 区分事实、观点和争议

## 4. 技术建议

主业务继续使用 Go。

文档处理复杂后，增加独立 Python 任务：

```text
Go API
├── 上传与任务管理
├── 知识库查询
└── AI 回答编排

Python Worker
├── PDF / EPUB 解析
├── OCR
├── 章节识别
├── 文本切片
└── 实体提取
```

第一版不要提前拆 Python 服务。

## 5. 版权边界

个人本地知识库与公开网站展示不是同一个问题。

公开网站应避免：

- 提供整本书下载
- 展示大段连续原文
- 用生成内容替代购买原书

更合理的方式是：

- 展示少量必要引用
- 标明出处和页码
- 重点展示自己的归纳、地图解释和观点对比
